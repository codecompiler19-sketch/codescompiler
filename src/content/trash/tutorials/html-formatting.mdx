# HTML Formatting

HTML Formatting is an important part of building a product specification with HTML. In this lesson, you will learn strong, em, mark, small, del, ins, sub, sup, and semantic versus visual formatting. The examples are original and use realistic content rather than meaningless placeholder text.

HTML describes **meaning and structure**. CSS controls presentation, while JavaScript adds behavior. Keeping those responsibilities clear makes pages easier to access, search, test, and maintain.

## What you will learn

This tutorial explains the core syntax, the most useful variations, correct usage rules, browser behavior, accessibility implications, SEO considerations, and how the topic connects to CSS and JavaScript.

## Core concept

Start by asking what the content represents before choosing markup. A browser can often display incorrect markup, but visual output alone does not prove that the document is correct. Screen readers, search engines, browser tools, automated tests, and future developers rely on the structure expressed by HTML.

For this topic, the central idea is **strong, em, mark, small, del, ins, sub, sup, and semantic versus visual formatting**. Prefer the native element or attribute designed for the job. Add CSS for appearance and JavaScript only when the interaction cannot be expressed by normal HTML.

> **Tip:** Test an example without CSS first. If the content remains understandable in source order, your HTML structure is probably doing its job.

## Basic syntax and a first example

HTML elements generally use an opening tag, content, and a closing tag. Void elements such as `img`, `input`, `meta`, `link`, and `br` do not wrap content. Attributes belong in the opening tag and provide additional information or behavior.

```html
<section class="lesson-section" aria-labelledby="lesson-heading">
  <h2 id="lesson-heading">A useful website section</h2>
  <p>The markup communicates what this content is before CSS changes how it looks.</p>
</section>
```

The `class` is reusable. The `id` is unique in the document and connects the heading to the section. The accessible name relationship is explicit rather than dependent on visual styling.

## Main elements, attributes, and variations

The exact choice depends on context, but the following table covers the most important concepts for this lesson.

| Feature | What it communicates | Practical guidance |
| --- | --- | --- |
| Native HTML element | The content's role or relationship | Use it before inventing a `div`-based component. |
| `class` | A reusable styling or scripting hook | Use clear, stable names; multiple elements may share a class. |
| `id` | A unique document identifier | Do not duplicate it; use it for labels and fragment links. |
| Accessible name or alternative | What a non-visual user needs to understand | Provide labels, text alternatives, or captions when applicable. |
| CSS | Visual presentation and layout | Keep colors, spacing, and responsive rules out of HTML. |
| JavaScript | Dynamic behavior and data updates | Preserve a usable HTML fallback whenever possible. |

### Content and nesting rules

Nest elements completely. If an element opens inside another element, it must close before the outer element closes. Use valid parent-child relationships and keep the source indentation consistent so errors are visible during review.

```html
<article>
  <header>
    <h1>Clear content hierarchy</h1>
  </header>
  <p>Related content stays inside the article that owns it.</p>
</article>
```

### Attributes that deserve attention

Use quoted attribute values and lowercase names. Boolean attributes are true when present, as in `required`, `checked`, `disabled`, or `hidden`. Use `data-*` for private application data and use ARIA only when native HTML cannot express the required relationship or state.

## Accessibility and SEO

Use the element that best describes the content. Keyboard users should be able to reach and operate interactive controls. Meaningful images require useful `alt` text; decorative images should use `alt=""`. Controls need visible labels, and focus indicators must remain visible.

Search engines benefit from a logical document hierarchy, descriptive titles, useful link text, semantic landmarks, fast media, and content that answers a visitor's intent. Avoid keyword stuffing and do not use heading elements merely to obtain a large font size. Use CSS for visual scale.

If this topic is driven by JavaScript, update the relevant semantic state as well as the visual state. For example, a collapsed navigation button should expose `aria-expanded` and `aria-controls`, not just change color.

## Common beginner mistakes

1. Choosing an element because its default appearance looks convenient instead of choosing it for meaning.
2. Omitting labels, alternatives, captions, or relationships that other users need.
3. Duplicating IDs or using invalid nesting and relying on browser repair.
4. Using `<br>` for layout or a table for page layout instead of CSS.
5. Trusting client-side validation or hiding content without considering keyboard and screen-reader behavior.
6. Adding ARIA roles that conflict with native semantics.

## How it works with CSS and JavaScript

CSS can select an element by type, class, ID, attribute, or state. Prefer classes for reusable presentation. JavaScript can select elements, listen for events, and update attributes or text. Prefer `textContent` for untrusted text and avoid turning a non-interactive element into a fake button.

```html
<button type="button" class="action-button" aria-expanded="false" aria-controls="extra-information">
  Show details
</button>
<div id="extra-information" hidden>
  <p>Additional information is available when the visitor requests it.</p>
</div>
```

The HTML remains meaningful before JavaScript runs. A script can toggle `hidden` and `aria-expanded` while CSS handles the visual transition.

## Validation and testing checklist

- Confirm the document has a doctype and a meaningful `lang` value.
- Check that every `id` is unique and every relationship points to an existing ID.
- Test the page with CSS disabled and with keyboard navigation.
- Resize the viewport and inspect long text, zoom, and small screens.
- Check images, forms, media, and embedded content for useful alternatives.
- Validate the markup and inspect the browser accessibility tree.
- Test server-side validation whenever user input is involved.

## Summary

| Key takeaway | Why it matters |
| --- | --- |
| Choose HTML for meaning | Browsers, assistive technologies, and search engines depend on structure. |
| Keep markup valid and nested | Predictable structure prevents difficult CSS, JavaScript, and accessibility bugs. |
| Use native features first | Native controls provide keyboard behavior and semantics for free. |
| Add accessible names and alternatives | People need equivalent ways to understand and operate the page. |
| Separate HTML, CSS, and JavaScript | Clear responsibilities make a project maintainable. |
| Test beyond the visual preview | Keyboard, zoom, mobile, and assistive-technology tests reveal real issues. |
